# 整理标准 v1

## 范围与证据

只收录授权范围的用户正文和助手最终回复。按来源类型和消息结构排除系统注入、环境信息、工具与推理、自动化提示及自动回执；不能仅凭 user/assistant 角色认定为人工讨论，也不能因正常用户引用了“heartbeat”等词就整条删除。混合消息中能依据结构分离的正文保留其原始片段并在来源记录标明提取方法；不能可靠分离时登记读取缺口，不改写成所谓原话。带附件消息仍保留可辨识正文，附件本身不支持不等于文字缺失。不把代理自动回执当用户授权。每条消息保留真实稳定 ID、角色、原文和 ISO 日期；只有回合时间时注明“轮次开始时间”。无法取得时间时登记缺口，不猜日期。只取得摘要或截断内容时不得做“完整原文”引用。

同批固定采集截止点，当前窗口不追读自己的新增回复。按窗口保存方法、目标日期、实际最早/最晚消息、分页终点、完整/部分/失败、缺口与重试入口；它们描述实际读取结果，不是计划。

## 事情边界与命名

按读者日后要找的具体目标或交付物归并，先查已有事项：多窗回答同一问题可以合并；同窗交付两件可以分别找回的成果应拆开。服务同一交付物的正文、标题、封面可保留分支。既有混合事项重整时保留原 ID 及已有链接：原卡可作为明确命名的汇总入口，用已有 workBranches 区分历史节点；如确需独立卡，沿用原卡承接主目标，用 related 连接新目标，避免两卡重复整段。普通增量不会删除旧节点，不靠省略字段搬迁历史。旁支不足成事，保留原文供搜索。

事项标题写用户认得的对象名和目的；有依据的俗称可放 terms；已有卡改名不换 ID，原完整标题也留在 terms 供按旧名搜索（原名含敏感参数时只保留安全的辨识词）。标题、小结用资源名或文件名表达内容，不搬运机器路径、带凭据的链接参数或流程指令；讨论路径本身时保留必要且不含私密信息的部分。原文及来源不因此改写。

## 小结、节点、日期与决定

- **事项 summary** 先写最新结果或停点，再补必要的目标与边界。结合较晚证据重写，不追加每批流水账；旧消息不覆盖新进展。短问答一句即可。recap 仅保留理解结果需要的背景与取舍，不和 summary 重复，无额外信息可留空。
- **节点 title / event**：左栏标题说清这段发现、决定或改变了什么；小结只补理解它所需的结果、理由或条件。不能用角色加原话开头、截断半句或“已写入指定文件”代替提炼。简短批准要结合上一条写出批准的方案，指代不清不猜。新收录的寒暄、无独立信息的回执不必单列。quote 仍与对应 thread + messageId 的正文、角色、时间严格一致。
- **每日小结** 按同一事项当天所有相关节点，写今天新增的事实、转折、决定或停点；只有讨论时就写具体讨论对象。不同分支分别点明，不拼接当天首尾原话，不把以后才知道的结论提前。同日多批更新要合看此前当天内容。
- **决定与变化** 记录会约束后续执行的明确采用、否定、改选或范围限制，标明有证据的前后变化，引用实际决定的节点。区分用户的选择、助手的建议与完成回执；不把同一决定换种说法再记一次。没有决定不凑数。

| 来源证据 | 允许结论 | 禁止跨越 |
| --- | --- | --- |
| 用户明确采用/否定/限定 | 用户确认、要求或否定 | 把较新的未采用建议覆盖用户决定 |
| 助手说完成/合并/发布 | 助手报告完成，外部结果本轮未核查 | 声称已独立核验文件或平台 |
| 候选方案交付 | 方案已提出，尚未采用 | 写成已实现 |
| 没有后续 | 截至所读范围未见确认 | 根据沉默判定尚未完成 |
| 明确放弃/结束/私有化 | 按原意区分停止、完成、仅自己可见 | 私有化等于删除 |

若用户从旧目标转向新目标，且两者拆为独立事项，把明确结束或转向的原文同时关联到受影响的旧事项，补其决定、日期和当日变化，并用 related 连接新事项；避免旧事项只有小结说已放弃，时间轴却停在更早的开发阶段。

## 主分类

默认六类按主要目标单选，定义以工作台 `config/default-types.json` 为准；`config/item-types.json` 为用户修正，优先于 AI。AI、视频、Codex 或具体行业不是默认分类轴。

- 写视频稿：独立写稿目标可归写作与编辑；整体视频交付归设计与制作。
- 开发同步脚本：编程与工具；使用脚本归档笔记：整理与事务。
- 分析调研数据以理解结果：学习与研究；据此选择方向：规划与决策。
- 无法判定：未分类，不按出现频率最高的工具名猜。

## 接续候选

“有明确接续”：明确要求继续或目标未完成，且没有较晚完成/终止证据。
“状态待核实”：确有具体可继续事项，但进展或继续意愿不明。不把每条 AI 建议、旧故障、习惯性自动任务当候选。

按**具体目标**对照用户原话、实际交付和同目标较晚的收尾，不只读最后一条回复。首轮调研、草案或部分交付完成后，用户原先要求的后续成果仍有明确缺口，就列为明确接续。用户已经决定做，正在等用户提供时间、对象等执行细节，也属于明确接续；如果不清楚的是用户还要不要做，才列待核实。助手单方面建议下一步、或对话日期很近，都不是继续意愿的证据。

明确完成或放弃：retireTasks 引用对应证据节点，保留历史事项。用户网站上的确认/移出只是浏览器选择；整理不读取或覆盖这些选择。相同目标延用任务 ID，新独立目标才建新 ID。

曾因缺页标为待核实的事项，在缺页补齐或关联窗口收录后，重新核对小结、stop、reason 和 openQuestion，去掉已失效的“早页未读”等采集过程说明。读取完整不等于事情完成：仍有业务上的未知，就写清具体待确认的内容，不沿用已解除的读取缺口，也不自动清空候选。

## 每批人工核验

每批执行[整理与发布检查](quality-review.md)。脚本能核验引用；语义验收须回到原话。复核结果保留在私有运行目录，不把真实案例放进分享包。
